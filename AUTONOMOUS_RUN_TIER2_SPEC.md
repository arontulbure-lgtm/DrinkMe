## T2-5: Account deletion, including the Firebase user
- **Today:** no server route and no client code. A token for a removed user already counts as logged out (`getUserId`).
- **Route:** `POST /api/users/:id/delete-account` with `{ idToken }` (POST because some proxies strip DELETE bodies). `requireAuth` + ownership (403). In Firebase mode the token must verify with a matching uid (401 or 403), so a stolen JWT alone cannot delete an account. Returns `{ deleted: true, firebaseDeleted: boolean }`.
- **Sequence, so a crash cannot lose the request:**
  1. Add `{ uid }` to a persisted `pendingAccountDeletions` list and save. If the save fails, undo it and return 503 with nothing changed.
  2. Run `deleteUserDataCascade(uid)`, idempotent, then save. A failure here is logged and the steps below still run. The cascade repeats at startup.
  3. Call Firebase Admin `deleteUser(uid)`. Treat `auth/user-not-found` as success. On success remove the pending entry and save.
  4. On Firebase failure, keep the entry and retry at each startup and when that uid tries to sign in. `/api/auth/mobile` for a pending uid returns 410 `{ code: 'account_deleted' }`, without creating a user.
- **The cascade removes:** the user record and all their posts through `deleteDrinkCascade`; their comments on other posts; their cheers (decrementing `cheersCount` on remaining posts) and saved set; `smartBarByUser`, `notificationsByUser`, `limitEventsByUser`; their id from all `partnersByUser` sets and `partnerRequestsByUser` both ways; `blocksByUser` both ways; reports they filed, and open reports against their content or account; notifications others received about them (add `actorId` in `pushNotification` from now on; for older entries also match on the message starting with the display name, skipping the "Someone" fallback).
- **Added after T2-13:** the cascade clears `partnerRequestsByUser` both ways, partner links on both sides, and `partner_request` notices. `partnersByUser` is not pruned at load, so a dangling link could come back if the same uid signs in again: test this.
- **Added after T2-3 and T2-10:** the cascade also removes reports they filed and resolved reports against them, clears `reporterId` and `resolvedBy` where they name the user, and removes the user's `avatarHashByUser` and `mediaCache` entries and any `actorId` notifications. `avatarClearedByAdmin` goes with the user record. Multi-post restores must run in reverse order.
- **Backups:** add retention for `${DB_FILE}.corrupt-<ms>` and `.pre-migration-<ms>`, default 30 days via `CORRUPT_BACKUP_RETENTION_DAYS`. Age comes from the filename timestamp; only exact name matches are removed. Purge at startup only after a successful `[db] Loaded` (never on a start that just made a backup), and again every 24 hours. Each deletion logs the count of remaining backups and the date of the last expiry, with no uid. Update the related comment; this deliberately changes T1-10's "never deleted".
- **What code cannot do (must go in the privacy docs and the final summary):** remove one person from a corrupt backup: their data stays up to 30 days. Restoring a backup brings deleted accounts back; an operator must repeat the deletions. Host snapshots, volume backups and hand-made copies are out of reach. Older request logs can contain the uid in URLs. A crash can leave a `.tmp-*` file until next startup. Copies on other users' phones and image caches stay until they refresh. Google-hosted provider photos are outside this system.
- **Client:** a Delete Account item in EditProfile's Account section leads to a confirmation that requires typing the confirm word. Password accounts re-authenticate with `reauthenticateWithCredential`; Google accounts use `getIdToken(true)`. On success call `logout()`; T2-8 clears the cache.
- **Strings:** `deleteAccount.action`: "Delete account" | "Șterge contul". `deleteAccount.warning`: "This permanently deletes your profile, posts, comments, saved posts and Smart Bar. Backup copies are removed within 30 days." | "Acest lucru îți șterge definitiv profilul, postările, comentariile, postările salvate și Smart Bar. Copiile de siguranță sunt eliminate în cel mult 30 de zile." `deleteAccount.typePrompt`: "Type DELETE to confirm." | "Scrie STERGE pentru a confirma." `deleteAccount.confirmWord`: "DELETE" | "STERGE". `deleteAccount.passwordPrompt`: "Enter your password." | "Introdu parola." `deleteAccount.wrongPassword`: "Incorrect password." | "Parolă incorectă." `deleteAccount.failed`: "Could not delete your account. Please try again." | "Nu am putut șterge contul. Încearcă din nou." `deleteAccount.done`: "Your account has been deleted." | "Contul tău a fost șters."
- **Tests (Firebase stub needs a `deleteUser` that can succeed, fail or report not-found):** a cross-account fixture covers every collection, then a search of the saved temp DB finds no trace of the uid, name or email. The other user's data and correct counts remain. Old JWT 401; non-owner 403; bad or mismatched `idToken` refused. First save fails: 503, nothing changed. Crash simulation with a pending entry: cascade completes at startup. Firebase failure leaves the entry, a retry clears it, sign-in returns 410. - **Device checks:** full flow for password and Google, wrong password, offline.
- **AC:** after success, the account and every listed data type are gone from the live DB and Firebase; a failure at any step is recoverable; backups expire on schedule; the limits are stated to the user.
- **Risks:** irreversible by design. Recovery from a corrupt DB must happen within 30 days. Google accounts do not re-authenticate, which is weaker. **External:** Apple sign-in later needs token revocation. Firebase deletion not run against the real project. ## T2-7: Email verification behind a flag
- **Today:** `emailVerified` is stored but not used for access; `src` has no `sendEmailVerification`.

All reversible unless marked.
1. T2-6: store plain text and rely on output encoding in any future web client. One-time migration guarded by `dbSchemaVersion`.
2. T2-10: image bytes move to `/media` routes. Lists become `{ items, nextCursor }`. The 600 per 15 minutes media limit is a proposal.

6. T2-13: consent on through a flag; existing partnerships kept; list always restricted.
7. T2-11: the name can be postponed; the notice cannot.
8. T2-5: 30-day backup retention, reversing T1-10. Not reversible for any backup already purged.
